# Plan 24-01: User Authentication Screens & Token State

## Goal

Create the signup page (`/register`), login page (`/login`), and secure routing guards using Next.js 16 `proxy.ts` and cookie-based authentication, storing JWT tokens in cookies to support server-side checks.

## Requirements Addressed

- **FE-AUTH-01**: User signup page (`/register`) and login page (`/login`) render high-fidelity inputs and error banners.
- **FE-AUTH-02**: Submitting credentials saves the JWT access token in browser cookies and redirects to the home page `/`.
- **FE-AUTH-03**: Secure route guard (`proxy.ts`) checks the token cookie, blocking unauthorized access to `/` and redirecting unauthenticated users to `/login`.

## Success Criteria

1. User signup page `/register` and login page `/login` render input boxes and submit buttons matching typography, colors, and spacing in `24-UI-SPEC.md`.
2. Valid signup or login submissions write the JWT token to the `token` cookie and redirect the browser to the dashboard `/`.
3. Unauthenticated route requests to `/` or `/chat` are intercepted by Next.js `proxy.ts` and redirected to `/login` server-side.
4. Authenticated route requests to `/login` or `/register` are intercepted by `proxy.ts` and redirected to `/` server-side.
5. Production build (`pnpm run build`) and test suites run successfully.

---

## Threat Model

### Threats Identified

1. **CSRF (Cross-Site Request Forgery)**: Storing the token in a standard cookie allows browsers to send it automatically, opening up potential CSRF hazards for state-changing calls.
   - Mitigation: The backend REST API does not rely on automatic cookie submission; instead, the frontend custom `api-client.ts` explicitly reads the token via JS and sets it as the `Authorization: Bearer <token>` header on requests. Cookies are configured with `SameSite=Lax`.
2. **Brute Force Incursions**: Malicious actors could hit authentication routes repeatedly.
   - Mitigation: Defer to backend Rate Limiting (Phase 18 SlowAPI) which is already configured.
